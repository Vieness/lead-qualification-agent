# Development log

How the project was built: thirteen stages, each planned, approved and then implemented, with `make check` green at the end of every stage. The log records what each stage delivered and — more useful for a reviewer — what the checks found along the way and how it was fixed.

## Process

Every stage followed the rules in [`CLAUDE.md`](../CLAUDE.md):

1. **Analyse** the code and libraries involved (including small spikes against the real SDKs, e.g. LangGraph interrupts and the Anthropic structured-output helpers).
2. **Plan**: files, design, tests, open decisions with a recommendation.
3. **Wait for approval**, then implement.
4. **Verify**: `make check`, plus manual checks in Docker and the browser where relevant. Defects found by verification are fixed in the same stage and listed below.

## Key decisions

| Decision                                                     | Why                                                                                                        |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Lead qualification for an agency as the business case        | A real, measurable pain for the target employer's domain; natural guardrails and human-in-the-loop         |
| TypeScript / Node instead of Python                          | The role asks for Node.js, SQL, Docker and several LLM providers                                           |
| Deterministic supervisor, LLMs inside agents                 | Routing a business process must be auditable; the model adds value in extraction, search planning, writing |
| Scores and decisions in code                                 | Reproducible, explainable, testable; a manipulated model cannot raise a score or approve a lead            |
| Own `LLMProvider` with an OpenAI-compatible adapter          | One adapter covers OpenAI, Groq, OpenRouter, Gemini and local Ollama — free options for reviewers          |
| Native structured outputs, strict tools, `effort` for Claude | Current Claude models reject forced `tool_choice` and `temperature`                                        |
| PGlite for tests and the CLI                                 | Real Postgres semantics without Docker; the CLI works right after `pnpm install`                           |
| Heuristic injection detector + structural defences           | Free and testable; the structure (data blocks, code decisions, no side-effect tools) is the real defence   |
| Human approval as a database status                          | Nothing runs after approval yet; a checkpointer is the next step once replies are sent                     |
| Viability gate (budget < $5k or deadline < 2 weeks → cold)   | Found by the eval: a clear but unviable request scored warm                                                |

## What verification found

| Stage | Found by                   | Problem                                                                                                                                          | Fix                                                                                                                          |

| 3     | API research               | Forced `tool_choice` and `temperature` return 400 on current Claude models                                                                       | Structured outputs, strict tools with `auto`, `effort`                                                                       |
| 5     | output guard test          | The example result had `score: 82` but a breakdown summing to 52                                                                                 | Fixture now equals the real `scoreLead()` output, with a test that keeps it so                                               |
