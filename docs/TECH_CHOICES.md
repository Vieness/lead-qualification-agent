# Technology choices

Every choice below was made against the same criteria: the target stack of the role (Node.js, SQL, Docker, several LLM providers, multi-agent systems), reliability that can be proven with tests, and how easily a small team could take the project to production.

## Runtime and API

| Area             | Choice                                     | Why                                                                                                                                                                                                                                                                  | Alternatives considered                                                                             |
| ---------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Language/runtime | TypeScript (strict, ES2024) on Node 24 LTS | One language for API, agents and UI; static types make tool contracts and agent state checkable at compile time; Node is the stack the role asks for. Node 24 is the active LTS (Node 20 reached end of life in April 2026) and the minimum for current test tooling | Python (richer ML ecosystem, but a second language for a Node team), Node 22 (maintenance-only LTS) |
| HTTP API         | Fastify                                    | Fast, plugin-based, built-in pino logging and request ids, `inject()` runs e2e tests without opening a port                                                                                                                                                          | Express (no validation or typing built in), NestJS (DI and decorators are heavy for this size)      |
| Validation       | Zod 4                                      | One schema gives runtime validation and the TS type; the same schema validates env, HTTP input, tool I/O, LLM output, and converts to JSON Schema for tools                                                                                                          | io-ts (verbose), valibot (smaller ecosystem), JSON Schema + Ajv (types must be written twice)       |
| Packaging        | pnpm workspaces, Docker Compose            | One repo for API and UI with strict dependency isolation; `make up` starts Postgres + API + UI on Linux images, identical on any machine                                                                                                                             | npm workspaces (slower, looser hoisting), Turborepo (unneeded at two packages)                      |

## Agents and LLMs

| Area                 | Choice                                                                                                                                                                                                                          | Why                                                                                                                                                                                                                                                                                                      | Alternatives considered                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent orchestration  | LangGraph.js: deterministic supervisor (planner) + research, matching and writer agents                                                                                                                                         | The process is an explicit graph with conditional routing, cycles (policy rewrite, tool loop) and a recursion backstop. The supervisor is code so the route is auditable; LLMs work inside agents, and only the matching agent runs a free tool-use loop where it adds value (planning English searches) | OpenAI Agents SDK (tied to one vendor), LLM supervisor (cost and unpredictability without benefit), custom orchestrator (more code to prove correct) |
| Human approval       | Lead status `pending_approval` → `approved` in Postgres + approve endpoint (refused without a draft)                                                                                                                            | Nothing in the graph runs after approval (sending email is out of scope), so a persisted checkpoint would add tables without value                                                                                                                                                                       | LangGraph `interrupt` + Postgres checkpointer (the next step once approval must resume work, e.g. sending the reply)                                 |
| LLM access           | Own `LLMProvider` interface + Anthropic / OpenAI-compatible / Mock adapters                                                                                                                                                     | Providers switch via env; one OpenAI-compatible adapter covers OpenAI, Groq, OpenRouter, Gemini and local Ollama (free options for reviewers); deterministic mock for tests                                                                                                                              | Vercel AI SDK, LangChain chat models (both fine, but hide retries/timeouts we want to control and test)                                              |
| Default Claude model | `claude-opus-5-5` with per-call `effort` (`low` for extraction, `medium` for writing)                                                                                                                                           | Anthropic's recommended default; effort replaces temperature/thinking budgets on current models and keeps simple calls cheap                                                                                                                                                                             | `claude-sonnet-5-5` (half the price; one env change)                                                                                                 |
| Structured output    | Native structured outputs (`output_config.format` / `response_format: json_schema`) + Zod validation with error feedback                                                                                                        | The provider constrains the shape, Zod enforces the rules JSON Schema cannot (e.g. budget min ≤ max); invalid output gets one corrected retry instead of failing the run                                                                                                                                 | Forced tool calls (rejected with 400 by current Claude models), parsing free text                                                                    |
| Reliability          | Own retry/timeout decorator; SDK retries disabled                                                                                                                                                                               | Every attempt is visible and traced; only transient errors (timeout, 429, 5xx, network) are retried, with exponential backoff + jitter and `retry-after`; refusals go to a human instead of being retried                                                                                                | SDK built-in retries (invisible to tracing and tests)                                                                                                |
| Refusals             | Server-side fallback (`fallbacks: "default"`, beta) + `refusal` handling                                                                                                                                                        | A refused request is retried on another Claude model inside the same call; if the whole chain refuses, the lead goes to human review                                                                                                                                                                     | Treating refusals as generic errors                                                                                                                  |
| Guardrails           | Layered: data blocks in prompts, code-made decisions, no side-effect tools for the LLM, heuristic injection/spam detectors (EN/UK, homoglyph and spacing normalisation), code checks on the draft, one pure `decide()` function | Deterministic, free and fully testable; a missed attack still cannot change scores or send anything, and every suspicion goes to a human                                                                                                                                                                 | LLM-based classifier (planned as a second layer; costs a call per lead and needs its own eval), no guardrails                                        |
| Business decisions   | Plain TypeScript rules (scoring, viability gate, approval threshold, policy checks)                                                                                                                                             | Reproducible, explainable and unit-testable; the LLM only extracts facts and writes text. A viability gate caps unviable leads (budget below $5k, deadline under 2 weeks) at cold so a well-written but impossible request never looks warm — found by the eval                                          | Letting the LLM score leads (non-deterministic, hard to audit), weighted-sum only (rewards clarity over viability)                                   |
| Prompts              | Versioned `prompts/*.md` with YAML frontmatter                                                                                                                                                                                  | Prompts are reviewed like code; the version used in each run is stored in the trace                                                                                                                                                                                                                      | Inline strings (no history, no versioning)                                                                                                           |

## Data

| Area             | Choice                                       | Why                                                                                                                                                                                        | Alternatives considered                                                                                 |
| ---------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| Database         | PostgreSQL 16                                | Relational data (leads → runs → tool calls) with FKs and transactions, `jsonb` for the agent outcome, built-in full-text search, pgvector in the same image when semantic search is needed | MongoDB (no FKs/transactions across documents by default), SQLite (no concurrent writers in production) |
| ORM / migrations | Drizzle ORM + drizzle-kit                    | SQL-like typed queries, no code generation step, plain SQL migration files in git; runtime migrator so production images do not need dev tools                                             | Prisma (codegen, heavier client, weaker raw SQL), Knex (no types), TypeORM (decorators, weaker typing)  |
| Enums            | pg enums generated from Zod enums            | Contracts are the single source of truth; the database rejects values the code does not know                                                                                               | Free text columns (silent bad data)                                                                     |
| Portfolio search | Postgres full-text search (`tsvector` + GIN) | Deterministic and testable, no embedding provider or extra API key, weighted ranking (title > summary > body), OR-query sanitised against tsquery injection                                | pgvector + embeddings (better for synonyms; planned as an upgrade), Elasticsearch (another service)     |
| Data files       | Markdown + YAML frontmatter (`yaml` package) | Case studies and prompts are human-editable and reviewable in PRs; frontmatter is validated with Zod and errors name the file                                                              | JSON (awkward for long text), gray-matter (unmaintained)                                                |

## Quality and operations

| Area            | Choice                                                                                                                                                                                       | Why                                                                                                                                                                                                                                                                         | Alternatives considered                                                                                        |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Tests           | Vitest (+ coverage-v8, 80% gate) and a sample-based eval (`pnpm eval`)                                                                                                                       | Fast, native TS/ESM; unit → integration → e2e plus 20 business samples with expectations that also run against a real model                                                                                                                                                 | Jest (needs extra ESM/TS setup), promptfoo (another config language for the same checks)                       |
| Test database   | PGlite (Postgres compiled to WASM)                                                                                                                                                           | Real Postgres semantics (FKs, enums, tsvector, transactions) in-process: tests need no Docker, start in milliseconds and run the same in CI and on any laptop                                                                                                               | Testcontainers (same engine as prod but needs Docker running), mocking the DB (tests prove nothing about SQL)  |
| Logging/tracing | One pino logger for HTTP and agent; run context via AsyncLocalStorage; trace (plan, tool calls, LLM calls, retries, tokens, duration) in `agent_runs`/`tool_calls`, optional `traces/*.json` | Every log line of a run carries its traceId without threading a logger through every function; a retry inside the shared provider is still attributed to its run. Logs carry metadata only (payload shapes, never free text), the stored trace keeps pattern-masked content | Langfuse / OpenTelemetry (good production next step; the event names map to spans), console.log                |
| UI              | React 19 + Vite, plain CSS tokens, hash routing; types imported from the API contracts (`import type`), Vitest + Testing Library                                                             | Three screens need no router, state library or UI kit; one set of types for the whole stack; light/dark and mobile from CSS alone; nginx serves the bundle in Docker                                                                                                        | Next.js (SSR not needed), react-router / react-query (weight without benefit at this size), Tailwind / UI kits |
| CI              | GitHub Actions: lint, format, typecheck, test, build                                                                                                                                         | Every check a reviewer would run locally, on each push                                                                                                                                                                                                                      | —                                                                                                              |
